# Commands

Every command prints short plain text, so the main agent's context stays small. `hrk <command> --help` lists every flag.

## Setup

| Command | What it does |
|---|---|
| `setup [--claude-config DIR]… [--force] [--no-hook]` | Installs the main-agent skill and the auto re-arm hook, and creates the config and state. A second run prints `no changes`. |
| `doctor [--claude-config DIR]… [--tools]` | Checks every dependency and prints the fix for each problem. `--tools` also lists the optional tools the project stage templates use when present; a missing one is never a failure. |
| `uninstall [--claude-config DIR]… [--purge [--yes]]` | Removes what `setup` installed; `--purge` also deletes config and state. |
| `upgrade [--version vX.Y.Z] [--check] [--yes] [--claude-config DIR]…` | Installs the latest release, or the named one, after verifying its checksum, then runs the new binary's `setup` for the given folders, the default one and every `~/.claude*` folder that holds the kit's skill, and names each. `--check` only shows what would change. It asks before a new major version, or before 1.0 a new minor one. |
| `version [--json] [--check]` | Prints the version, schema and contract. `--check` also asks GitHub for a newer release. |

See [setup.md](setup.md) and [upgrading.md](upgrading.md).

## Main session

Commands that take text (`spawn`, `send`, `answer`) also accept `--stdin`, so the main agent passes your words through a quoted heredoc instead of a shell string. The text may be up to 100 KiB, since the agent receives it as one command-line argument.

| Command | What it does |
|---|---|
| `spawn [flags] -- <prompt>` (alias `run`) | Records a task and returns at once. A detached launcher opens the runner in a new herdr tab, or a new worktree workspace, and sends the first prompt. |
| `wait` | Blocks until one of your tasks has news, prints one line per event and exits. Run it in the background and rerun it after each wake. |
| `answer <id> <text>` | Answers a runner that reported `needs-human`. It continues in the same session. The id may name the runner's attempt, such as `t3a2`; an answer for an attempt that ended is refused. See [Context handoff](#context-handoff). |
| `answer --from-telegram --stdin` | Routes a Telegram reply by its `#id` tag, or to the only waiting task. See [telegram.md](telegram.md). |
| `main [--exec]` | Prints, or runs, the command that starts the main session with the skill and the Telegram channel. |
| `send <id> <text>` | Types a new prompt into a live runner. A `done` or `failed` task whose tab is still open becomes `running` again, and its next report wakes `wait`. A `stopped` task refuses it. |
| `release <id> [--note TEXT]` | Opens a held task's human gate and starts it. |
| `plan run <plan.md\|dir> [--dry-run] [--parallel N] [--branch NAME]` | Runs an AgentKit plan one fresh runner per phase, in waves on one branch. See [Plans](#plans). |
| `list [--all]` | Your tasks and every project's, or every owner's with `--all`: stored status, herdr's live state, the TAB column (`open` with when `gc` closes it, `kept until HH:MM`, `kept`, `closed`, or `-` before a tab exists), AGE since the spawn and LAST, the age of the task's latest event, followed by the runner's compactions, such as `2m, 3 compactions`. A later `plan run` phase has `(in tN's worktree)` after its title. |
| `show <id> [--prompt] [--events N]` | One task as compact text: status, kind, agent, title, project and stage, times and tab, `context:` (the attempt after a handoff, and the compactions), worktree (for a later `plan run` phase, the first phase's, such as `worktree: <path> on <branch> (of t5)`), the `git:` line, error, summary (whole), decisions, question, outputs, the last 5 events and the output folder. Other fields are cut to 400 characters. The prompt and the inputs from `--after` tasks show only with `--prompt`. |
| `show <id> --json [--events N]` | The task as one JSON object and nothing else, for scripts. With `--events` it prints `{"task": …, "events": […]}`. Parse this, never the text view. |
| `peek <id> [--lines N]` | The last lines of the runner's visible pane (default 30, at most 200), with anything that looks like a secret hidden. It only reads, and refuses a task whose tab is closed. |
| `events [--since 1h] [--task ID] [--follow] [--timings]` | The event log, or the measured latencies per task. |
| `events --learning [--since 1h] [--task ID] [--project NAME]` | Per task: kind, agents, status, attempts (starts, plus sends that reopened a finished task), nudges (at a turn end without a report, or for no visible progress), sends, answers, `needs-human` reports, unreported turns, agent switches, DURATION from spawn to last finish, ACTIVE (time in working rounds, from a start, send or answer to the next report or stop; a time on the task that includes turns idled without a report), STALLED (time blocked on a prompt or stalled), IDLE-KEPT (time a kept tab stayed open after the finish, or `-`), and time waited on a human after the spawn. Open rounds and stalls count up to now. Every number comes from the event log. |
| `focus <id>` | Switches herdr to the runner's tab. |
| `stop <id>... [--remove-worktree]`, `gc [--kept] [--owner X \| --all]` | Quits runners and closes their tabs. `stop` takes several ids, prints one line per id, still stops the others when one fails, and names the ids that failed. For a task without a worktree it notes up to 5 untracked files the runner may have left in the checkout, and deletes none. For a worktree task it notes that the runner's herdr workspace stays open on the worktree until `cleanup` or `stop --remove-worktree` removes it, and the `closed` event says `agent quit; workspace kept`. `gc` closes the runners of this main session and of every project, or of one main session with `--owner`, or of every main session with `--all`, that finished at least 30 minutes ago (`--older-than`), and kept runners once they finished `keepFor` ago (see `keep`), except a runner whose agent is working or blocked because someone kept using its tab; `wait` does the same for its owners' runners while it watches, and the auto re-arm hook once nothing is left to watch. `gc --kept` also closes kept runners that finished at least `--older-than` ago. Worktrees and branches are kept unless removal is asked; `gc --remove-worktree` also closes kept runners. See [Closing runners](#closing-runners). |
| `sync <id> [--from REF] [--no-send]` | Merges origin's default branch (such as `origin/main`), or `--from REF`, into the branch checked out in the task's worktree, then asks the runner to re-run its checks and report. See [Syncing a branch](#syncing-a-branch). |
| `keep <id> [--off]` | Keeps a finished runner's tab open for the config's `keepFor` after it finished (4 hours by default; `0` means until `keep --off` or `stop`). `--off` lets `gc` close it again, at once when its close time has passed. Running a project stage again turns keep off for the stage's earlier finished runs. |
| `cleanup [id]... [--yes] [--no-fetch] [--owner DIR]` | Fetches origin, then lists the finished worktree tasks of the current folder's owner and of every project (only `--owner` with that flag) whose worktree or branch is still there, as `merged`, `unmerged`, `dirty` or `kept`. `--yes` removes the worktree and deletes the local branch of each merged one, or of the given ids. See [Cleaning up](#cleaning-up). |

## Projects

A project is a git repository the kit keeps a record for, so a main session can drive it from any folder.

| Command | What it does |
|---|---|
| `new <path> (--brief FILE \| --stdin)` | Starts a project: creates the folder and a git repository, keeps the original brief git-ignored under `handbook/product/discovery/brief/original`, writes the project record, makes one first commit of exactly the files it wrote, opens a herdr workspace and registers the project. `--remote URL` adds origin and never pushes; `--reference` names a repository to learn from; `--name`, `--initial-branch`. |
| `project status [name]` | Where the project stands: stage, gates, milestone, runners, tasks waiting on you, and one next step. It reads only the kit's record and tasks, never herdr, and changes nothing. Without a name: the project holding the current folder, else the only one, else one line per project. |
| `project register <path> [--name NAME] [--reference PATH]` | Registers an existing git repository, importing a committed `handbook/product/project.md` when there is one. The committed files name the reference repository by its origin URL (credentials removed) or its folder name, never by a local path; when the imported record has only a name, register says so, and `--reference PATH` gives the path on this machine. Nothing is written to the repository. It refuses a linked worktree; register the main checkout. |
| `project forget <name> [--yes]` | Removes the registry entry and the kit's record, never the repository. It refuses while the project has unfinished tasks or record changes not yet committed, unless `--yes`. |
| `project run <stage> [--stdin] [--after t1] [--gate auto\|human]` | Spawns a discovery stage runner from the kit's stage template; `--stdin` adds your notes as untrusted data. A `pack` given `--after` waits for `release` by default, with the reason "review the earlier stages before the pack; release to build it", so you can review the earlier stages first; `--gate auto` starts it on its own. Every other stage defaults to `--gate auto`. See **Discovery and gates** below. |
| `project approve\|changes\|reject <spec\|pack>` | Records a gate outcome for the committed version, with `--by` and `--note`, and commits the project's records. `changes` sends the feedback from stdin to the stage's runner. |
| `project share <stitch\|lavish-hosted> <on\|off>` | Records whether the project's runners may share work outside this machine. Off by default. |
| `project decide --stdin` | Keeps one decision of yours in the decision log. |
| `project cr decide <n> <now\|next\|backlog\|reject>` | Records your decision on a change request. See **Change control** below. |
| `project backlog add --stdin` | Keeps an idea as the next backlog item. |
| `project dep add <name>`, `project dep set <Dn> --status S` | Tracks what the project waits on outside itself. |
| `project milestone start <M>` | Starts a milestone: M0's scaffold runner and its close runner, or a later milestone's plan runner. See **Milestones** below. |
| `project milestone chain <M>` | Spawns the milestone's feature, integrate and close runners from its committed plan. |
| `project milestone done <M> [--merged-commit SHA]` | Records the milestone done once you merged its release branch, commits the records and tags it locally. |
| `project milestone reopen <M> --reason WHY`, `project milestone close <M>` | Puts a done milestone back in progress, deleting its local tag; spawns a new close runner after a reopen or a failed close. |
| `project graduate [--export DIR [--include-original]] [--yes]` | Removes the discovery folder from the tree in one commit and tags the commit before it. See **Graduation** below. |

`new` refuses `/`, your home folder or a folder above it, a folder that is a git repository (use `project register`), lies inside one or holds one, a folder that is, lies inside or holds a registered project, a non-empty folder without `--allow-non-empty`, a `.gitignore` that is not a regular file, a folder on the way to a file it writes that is a symbolic link, and a remote URL that holds credentials. With `--allow-non-empty`, an existing `.gitignore` is left unchanged and out of the first commit: the brief is ignored through `.git/info/exclude`, and the output prints the line to add to `.gitignore`. `new` checks that git ignores the brief before it commits. Nothing is deleted when a step fails; a remote, workspace or registry step that fails is reported as `not added`, `not created` or `not registered`. Runners cannot run `new`, `register` or `forget`. This check reads `HRK_TASK`, which spawn sets in a runner's tab; it guards against mistakes, not against a runner that sets out to get around it, so it is not a security boundary. A project stays `being set up` until `new` finishes; when `new` was interrupted, `project status` and `spawn` say so, and `project forget <name>` drops it. A later `new` with the same name takes over such a leftover once it is 10 minutes old and its folder holds no git repository.

**Discovery and gates.** `project run <stage>` renders the stage's template (`intake`, `spec`, `ux`, `design`, `architecture`, `roadmap`, `pack`, `change`, `graduate`) with the project's record and spawns its runner in the project; `project status` names the next stage. Two gates stop the project until you decide: the spec and the stakeholder pack. Every stage but `intake` and `spec` is refused until the spec is approved. `approve` reads the version from the committed artifact and refuses one that is uncommitted, changed or already decided. An outcome holds for the content it was recorded for, the spec file's git blob or the pack folder's tree: when that content changes under the same version, the gate opens again as changed since approval, and a new outcome replaces the old one, which the output and `decisions.md` say. Approving the pack imports the roadmap from the committed roadmap proposal: every text field of its yaml block becomes one line of at most 300 characters, a dependency's owner must be `user`, `vendor` or `runner`, dependencies match by name whatever the case, an import never clears a field you set, and done and running milestones keep their scope. A lite-track project may skip the pack only with `approve spec --waive-pack`, before the pack has an outcome; the spec gate is never waived. With the pack waived, the first `milestone start` that finds the roadmap proposal committed imports it the same way, with a decision that says so; until then only M0 may start, and M1 and later are refused with a pointer to `project run roadmap`. Dates in the records and `decisions.md` are your local dates; full times keep their UTC offset. Values that look like secrets are hidden in gate notes, `decide` entries and change request titles before they are recorded. Open change requests and dependencies not ready reach each runner's rules as a fenced block of untrusted data. Before building every wireframe or the whole prototype, the `ux` and `design` runners sample the one or two main screens (in `design`, as at least two visual directions under `design/directions/`) and ask you one round through `needs-human`; notes for the stage that say to skip it, or give a design system to follow, skip that round. The pack stage writes a self-contained `pack.html` and `pack.pdf` (DOCX with `--docx`) for you to share. Runners share nothing outside this machine, such as through Stitch or hosted Lavish, until you switch it on with `project share`.

**Change control.** A change after the spec is approved starts with `project run change --stdin`. Its runner writes the change request (CR) file and reports its class, `tweak`, `within-milestone` or `scope`, as `--decision "class -> <class>"`. `cr decide` then puts it into the running milestone (`now`), the next one, the backlog, or rejects it. The running milestone keeps its scope: a scope change decided `now` while a milestone runs needs `--blocking`, and one decided `now` or `next` after the pack was approved marks the pack as needing a new approval before the next milestone. `decide`, `cr decide`, `backlog add` and `dep` commit nothing; their records reach `handbook/product/` with the next gate outcome or milestone commit. A dependency records where its secret is kept (`--secret-location`), never the secret; a value that looks like one is refused. Runners that need it are spawned with `--gate human --reason "needs D<n>"`, and `dep set D<n> --status ready` lists them with the `release` command for each.

**Milestones.** A milestone starts after the pack is approved, or waived on the lite track, and after the milestone before it in roadmap order is done; `start` is refused while a scope change waits for a new pack approval. M0 builds the repository standard and an empty app, then its close runner. A later milestone starts with a plan runner whose plan answers its open questions with the recommended options and reports them as `decided:`; you may veto them before `chain`. `chain` reads the yaml block of the committed plan: a feature has at most one parent, an integrate node any number, and a final integrate node and a close runner are added after the leaves. Integrate nodes work on `integrate/<M>-<id>`, the close runner on `release/<M>`; when an existing branch inside such a name, such as `release/<M>/x`, keeps git from creating it, the runner gets `<name>-r<k>` and the output says so, and a branch named like a folder above it, such as `release`, is refused. Run `chain` again after a runner failed: done nodes are kept. The close runner writes the release notes on `release/<M>` and never merges, tags or pushes. You merge that branch through a pull request and pull; `milestone done` then finds the merge in the local default branch, imports the release's roadmap update unless an earlier `done` of the milestone imported the same file, commits the records and creates the annotated tag from the project record's `tagFormat` (`v0.{N}.0` by default) locally. After a squash or rebase merge, pass `--merged-commit`. Either way the release notes it finds must be those at the tip of the close runner's branch, locally or on origin, and not those of a release merged before a reopen. `reopen` deletes the local tag, refused once the tag is on origin; the merged release stays, and `close` prepares a new release branch `release/<M>-r<k>` after the fixes. The kit never merges into the default branch and never pushes.

**Parallel runners.** When more of a project's runners are active than the project record's `parallelWarning` (3 by default), a project spawn prints a `note:` and `project status` shows the count. Nothing is blocked.

**Graduation.** `project run graduate` writes `handbook/product/requirements.md`, keeps the approved pack in `handbook/product/approval/` and the open change requests in `handbook/product/changes/`, and rewrites links into the discovery folder. `project graduate` then checks and prints what it would do; `--yes` removes `handbook/product/discovery/` in one commit with the records and tags the commit before it `discovery-archive` (or `discovery-archive-<n>`), locally. It refuses until both gates passed, the discovery stages finished and the requirements are committed. Graduation does not purge history: every committed file stays reachable through the tag, and the untracked original brief stays on disk. If the commit is refused, the folder, the records and the export folder are put back as they were. After it, stages that work on the discovery folder are refused and the spec gate stays as decided. The pack stage still runs: after a scope change it builds the next pack from the requirements, `handbook/product/roadmap.md` and the change requests into `handbook/product/approval/pack-v<n>/`, and `approve pack` clears the re-approval that `milestone start` waits for.

**Owners.** Every task reports to an owner, and `wait`, `list` and the auto re-arm hook pick tasks by owner. A project task's owner is `project:<name>`. Any other task reports to the git top-level of the folder `spawn` runs in, or that folder outside a repository, even when `--cwd` points elsewhere. `spawn --owner` overrides both. `wait` and `list` take the current folder's owner plus every `project:` owner, so project news reaches the main session from any folder, including a project started after the wait began. They go by the task's owner, not the registry, so a `projects.json` that cannot be read stops only the project commands; `spawn` then warns once and starts a task without a project.

**Project tasks.** `spawn --project NAME` makes a project task; so does a spawn whose folder (`--cwd`, else the current one) lies in a registered project. It works in the project's folder unless `--cwd` names another place inside it. Its tab opens in the project's herdr workspace, which is opened again when you closed it; a worktree task creates its worktree from that workspace. When the workspace cannot be opened, the task opens where a task without a project would, and the event log gets a `project-workspace-fallback` event.

## Chaining

`spawn --after t1,t2` queues a task until every parent is done. The parents' summaries, outputs and worktree branches are added to the child's first prompt. A worktree child of a single worktree parent starts from that parent's branch unless `--base` says otherwise.

With `--gate auto` (the default) the child starts by itself within about a second of the last parent's report. With `--gate human` it moves to `held` and waits for `release`. `--reason TEXT` says why, such as `needs D2`; it shows on the `held` line, and a Telegram reply must then name the task to release it. A parent that fails or is stopped fails its waiting dependents.

A Claude runner uses the main session's Claude config folder, and so its account. `spawn --claude-config DIR` picks another one, as a path or a bare name: `claude2` means `~/.claude2`, and `claude` means Claude's default, `~/.claude`. Run `setup` and `doctor` for that folder too, so its herdr hook and permission prompt are ready.

A worktree branch is named `hrk/<id>-<slug>` unless `spawn --branch NAME` names it after the repository's own convention, such as `fix/CSD-11-paid-leave`. The runner commits on that branch and never creates or switches branches. When a worktree task gets the default name, `spawn` also prints a `note:` with the repository's recent branch names, so the next spawn can follow them with `--branch`.

## Plans

`plan run <plan.md|dir>` runs an AgentKit plan, a `plan.md` next to `phase-NN-<slug>.md` files, with one fresh runner per phase instead of one runner cooking the whole plan. Use it for a plan with phase files. For a plan without phase files, or a small one, `spawn --skill ak:cook -- <plan.md>` is still the right call.

- **Reading the plan.** Each phase file's frontmatter gives its `phase` number, `title`, `status` and `dependencies`; without `dependencies` a phase depends on the previous one, and `[]` makes it a root. A dependency on an unknown phase, or a cycle, is refused. A phase's write scope is the backticked repo-relative paths under headings that contain "file", such as `## Files`, `## Files to Modify` or `## Related Code Files`: a `:line` suffix is dropped, a path ending in `/` is a folder, one with `*` a glob, and a bare file name matches that name anywhere. A phase without such paths declares no scope.
- **Placement.** The first phase to run opens a new worktree on `--branch` (default `hrk/<id>-<plan slug>`). Every later phase works in that same checkout and branch, in a tab of that worktree's workspace while it is open. Phases run in waves: a wave starts when the previous one is done, and holds at most `--parallel` phases (default 2) whose dependencies are met and whose scopes are declared and disjoint. A phase without a declared scope always runs alone. Parallel runners are told to stage only their own paths and to retry on `index.lock`.
- **Flags.** `--dry-run` prints the waves, with each phase's dependencies, scope size and why it runs alone, and spawns nothing. `--kind` (default `flow`), `--agent`, `--claude-config`, `--language` and `--skill` (default `ak:cook`) apply to every phase runner. `--gate human` holds every phase after the first for `release`.
- **The brief.** Each runner gets the skill, the absolute phase file, which phase of which plan it runs, its write scope, and the rules: do only this phase, do not edit plan files, commit on the branch before reporting done.
- **Checking a phase.** When a phase reports `done`, the kit looks at the commits since the phase started and at the checkout: the files changed, those outside the scope (widened by the scopes of the phases that ran beside it; a commit that touches only a sibling's scope is the sibling's), the commit count and whether the checkout is clean. Files under `plans/` belong to no scope and untracked ones never make it dirty, and files an earlier phase left uncommitted are judged with that phase only. The verdict is `accepted`, `outside-scope`, `dirty`, `no-changes`, `no-declared-scope` or `unknown`, recorded on the task (`show --json`, field `phaseCheck`) and as a `phase-accepted` event. The kit then sets the phase file's `status: completed`. An `outside-scope` or `dirty` phase holds the next wave as `held` news that names the files, such as `phase 3 changed files outside its scope: a.go; release to continue`; `release` each held task to go on.
- **Plan status.** `plan run` sets `plan.md`'s `status: in-progress`, and `completed` once the plan is done. It changes only those frontmatter lines and never commits them.
- **Done.** When the last phase is done, `plan-done` news points to `<plan dir>/reports/plan-run-<YYMMDD-HHMM>.md`, which puts each runner's claim (summary and decisions) next to what the kit verified, and says how many phases were verified in scope.
- **Resume.** Run `plan run` again after a phase failed or was stopped. It refuses while a task of the plan is still running, queued or held. Phases whose latest task is done are kept, and so are phases with no task whose file already says `completed`. The run's worktree is reused while it exists; when it is gone, a new worktree starts from the run's last branch, so the done phases' work is kept. The rerun of a failed or stopped phase is told to continue from the partial work in the checkout. Its check starts at its own launch, so commits the earlier attempt made are not checked.
- **Guards.** `plan run` refuses inside a runner and for a plan outside a git repository. The first phase's worktree cannot be removed (`stop --remove-worktree`, `gc --remove-worktree`, `cleanup`) while another phase still works in it.

## Syncing a branch

`sync <id>` merges origin's default branch, such as `origin/main` where pull requests merged on the remote land, into a worktree task's branch, so a runner that fell behind can re-run its checks. It refuses while the task is starting, while its agent is busy, runs background work or cannot be checked through herdr, when the worktree has uncommitted changes, and when the worktree has left the task's branch. Only after these checks does it fetch origin, without pruning. The output names the ref merged; when the local default branch has commits origin lacks, it also suggests `--from main` (or the local branch's name) to merge those. A branch that already holds the ref is left as it is. A conflicting merge is aborted, the branch is unchanged, and `sync` prints the conflicting files and the text to hand the merge to the runner with `send`. A merge git refuses to start, for example because it would overwrite an untracked file, is reported as an error and changes nothing. `--no-send` merges without telling the runner. `sync` never pushes, rebases or touches another branch, and a runner cannot run it.

## Usage limits

When a runner's agent hits a usage limit, the task switches to the next agent in the config's [`quotaFallback`](config.md#keys) list. The new agent starts in the same tab and checkout, with the first prompt and a note to continue from the partial work. The event log gets an `agent-switched` event, and `events --learning` lists the agents the task went through.

Claude reports the limit itself: its turn ends in a `StopFailure` hook with a rate-limit error and its limit message. pi and omp report it the same way, through the kit's runner extension, when their turn ends on an error that names a usage limit, such as `You have hit your ChatGPT usage limit`, or credits or quota running out (`out of credits`, `insufficient_quota`). Their screens never count, because a tool's output can draw a line just like pi's own `Error:` line. With no fallback left, or none configured, that task fails with `usage limit reached for <agent>`, and its waiting dependents fail too. An error that only mentions a quota or an exhausted resource, such as a provider's `429 RESOURCE_EXHAUSTED` rate limit after pi gave up retrying, still switches to a fallback when one is left, but with none left it is `usage-limit` news, like a limit seen on a Codex screen, and the task keeps running.

Codex only shows the limit on screen, as its own `■ You've hit your usage limit …` error line; the same words in the conversation or in a tool's output never count. Such a line switches the agent when a fallback is left. Otherwise the task is not failed: the runner is nudged as for any unreported turn, and the main session gets `usage-limit` news saying the runner appears to be at its usage limit.

## Context handoff

A runner whose agent nears its context limit continues once in a fresh session of the same task, in the same tab and checkout. For Claude Code the kit asks at the first automatic compaction; a manual `/compact` never asks. For Codex it asks at a turn end when the footer shows `contextHandoffAt` percent of the context left or less (15 by default). For pi and omp it asks at either: at a turn end when the runner extension reports that much context left or less, or at the first automatic compaction. The runner commits or saves its work, writes `tasks/<id>/out/handoff-a<N>.md` and runs `report handoff`; the kit then quits the agent and starts attempt N with a prompt that points at the handoff. Each task hands off at most once. `contextHandoff: false` in the [config](config.md#keys) turns the requests off.

Attempts show only from the second one on: `wait` adds `attempt 2` to a `needs-human` line, Telegram tags it `#t3a2`, and `answer t3a2` or `answer t3` reach it, while `answer t3a1` is refused once attempt 1 ended. Reports and hooks from an ended attempt are refused or ignored. The event log gets `context-low` and `handoff`, and `processes-carried` when the previous session left processes running, which the new attempt is told to stop or reuse. See [report-contract.md](report-contract.md#context-handoff).

## pi and omp runners

A pi or omp runner starts with three files from its task folder: `contract.md`, the report contract, passed with `--append-system-prompt` so it survives compaction; `hrk-runner.ts`, the kit's runner extension, which reports each turn end, the context left and each compaction to the kit; and, for omp only, `omp-runner.yml`, a config overlay that turns off omp's `ask` tool and its terminal-title spinner (`tui.titleState: false`), so herdr's agent revision stays still and stall detection works. The skill is sent as `/skill:<name>`, with a colon in the name turned into a dash, so `--skill ak:plan` becomes `/skill:ak-plan`.

- Your own pi extensions still load in runners, next to the kit's; the kit does not turn them off.
- omp ends the background jobs a tool call starts with `cmd &` when that shell call returns, and pi leaves them running unseen. The contract tells runners to wait for background work before reporting; a runner that does not is nudged.
- Without its herdr integration (`herdr integration install pi` or `omp`), herdr cannot see the agent working, so stall checks go blind. `doctor` fails the check when your config uses that harness.
- The runner extension is the only way the kit learns that a pi or omp turn ended, so it is also how the kit sees unreported turns, usage limits and low context. If it stops working, for example after a pi or omp update renames the event it listens to (`agent_settled` in pi 1.2.0, `agent_end` in omp 18.2.10), an idle runner that never reported stays `running` and `wait` keeps waiting. The kit is tested with pi 1.2.0 and omp 18.2.10; after updating either, watch the first runner: one that sits idle in `running` without a `nudged` event means the extension no longer reports turn ends.

## Cleaning up

Finished runners close on their own (see `gc`), but their worktrees and branches stay until you remove them. `cleanup` without `--yes` only reports, however old a worktree is:

- **merged:** the branch, and the commit the worktree has checked out, are in the default branch (`origin/HEAD`, else `origin/main` or `origin/master`), no tracked file has changes, and no untracked file lies outside `plans/`. A branch merged with squash or rebase counts too: merging it into the default branch would change nothing (`git merge-tree --write-tree`, git 2.38 or later), and the list says `(squash or rebase)`. A branch whose changes were reverted on the default branch also adds nothing, so removing it loses no work. With an older git, or in a repository that configures a custom merge driver, only commits that landed as they are count. `cleanup --yes` removes these. Untracked files under `plans/` and ignored files are deleted with the worktree; the list says how many. When the last worktree of a repository goes, its now empty folder in herdr's `worktrees/` root goes too. The worktree and branch are checked again right before removal. Only a branch the task created is deleted, and only while it is still merged; a branch another worktree has checked out is kept.
- **unmerged:** the branch holds work the default branch lacks, or a squash merge conflicts with later changes there; delete it yourself when you know it landed.
- **dirty:** tracked files have changes, or untracked files lie outside `plans/`; the list names the first few. They are never removed.
- **kept:** the runner is kept open with `keep`. Run `keep --off <id>` first.

`cleanup --yes` never closes a runner whose agent is still working or waiting at a prompt; it skips that task, and a later run cleans it.

A worktree removed outside the kit, such as with `git worktree remove`, is marked removed the next time `cleanup` or `wait` looks. The runner's herdr workspace, left open on the deleted folder, is closed then, unless another unfinished task, such as a later phase of the same plan run, still works in it. When its branch is gone too, the task gets a `cleaned` event with "removed outside the kit"; otherwise the branch is still listed.

`cleanup` without `--owner` covers the current folder's owner and every project, as `list` does. Pass `--owner DIR` for one main session only.

While `wait` runs, it fetches origin at most every 10 minutes and reports each newly merged worktree once as `cleanable` news, so the main agent can ask you. Nothing is removed until you agree.

## What `wait` reports

The main agent runs `wait` in the background. In the session `main --exec` starts, the auto re-arm hook that `setup` installs also runs it after every turn, so no news is missed when the agent forgets to rerun it.

`wait` wakes for `done`, `needs-human`, `failed`, `held`, `stalled`, `stopped`, `turn-ended-unreported`, `usage-limit`, `cleanable`, `processes-left` and `plan-done`. Other events, such as `started`, `prompt-resubmitted`, `blocked`, `unstalled`, `nudged`, `interrupted`, `closed`, `process-check-skipped`, `notify-deferred`, `phase-accepted`, `plan-status-failed`, `context-low`, `handoff` and `processes-carried`, only move its cursor.

```
t3 done · fix login · git: on hrk/t3-fix-login, 1 commit, no upstream · tab closes 15:42 · Login fixed; tests pass · out: /…/tasks/t3/out/notes.md
t4 needs-human · drop legacy API · Q: Drop the v1 endpoint? (recommended: yes)
```

- A `done` or `failed` line carries `git:`, the state of the task's checkout when the runner reported: its worktree, or `repo state` for a task without one. It counts uncommitted and untracked files, naming the share under `plans/` (`1536 untracked (1530 under plans/)`), and commits not pushed, behind, diverged from the upstream, or with no upstream, and ends with `head <sha>`, the short sha of HEAD. For a task without a worktree it counts the commits made since the round began (the launch, or the latest `send` or `answer`): `2 commits since start, head abc1234`, so a runner that commits on the default branch itself is never reported as "no new commits".
- A `done` line says `tab closes HH:MM` when `gc` will close the runner, `tab kept until HH:MM` after `keep`, or `tab kept` with `keepFor: 0`.
- A `needs-human` line of a runner on its second attempt or later says so, as `attempt 2` after the title; answer it as usual. See [Context handoff](#context-handoff).
- A `done` line lists the runner's own decisions as `decided: …` right after the title, and a round of questions spans a header and one numbered line per question. See [report-contract.md](report-contract.md#question-rounds).
- Reports that land within 200 ms of each other wake it once.
- Each line is at most 300 characters. `show <id>` has the full detail.
- It only sees tasks of its owners: the git top-level of the current folder and every `project:` owner by default, or only `--owner`. So several main sessions can wait at once. Each owner has its own cursor, and a second `wait` on the same cursor exits with `already waiting`, naming the holder and its pid: the main session's auto re-arm hook, which wakes the agent on news, or another `hrk wait`.
- When every task has finished, it exits with an `idle:` line. A task that is `needs-human` or `held` keeps it waiting, because the answer or release can come from another main session's Telegram or from the runner's tab. It waits up to a second after the latest status change first, so news written right after that change is not lost.
- After 30 minutes without news it prints `timeout` and exits 0 (`--timeout` changes this).

While it runs, `wait` also watches each runner through herdr:

- An agent that exits without reporting fails its task. A launch that never finishes fails its task.
- A running or waiting task whose herdr pane is gone, or whose pane now holds another agent, as after a herdr or machine restart, fails with `runner lost: herdr pane gone` (or `… now holds another agent`) when `wait` starts and at each check a minute apart; its waiting dependents fail with it. `answer` and `send` to such a task say the runner is gone and point to `show <id>` for its worktree and branch.
- A runner whose agent exited and left only its pane's shell, as after a herdr restart whose `claude --resume` found no conversation, fails the same way with `the agent exited without reporting: <line>`, quoting the agent's last line above the shell prompt, such as `No conversation found with session ID: …`. The check looks again 15 s later before it fails the task, and keeps the runner when its agent is back or the task moved to a relaunch or a new attempt in between. A pane herdr has just restored, whose agent herdr has yet to detect (no kind, status unknown), is never failed this way; that detection took 35 s on a loaded machine.
- When a runner is failed as lost, the processes still running in its memory scopes (see [config.md](config.md#runner-memory-cap)), which a herdr restart no longer ends, are reported as `processes-left` news: `2 processes the runner started still run after its runner was lost: …`. The kit never kills them.
- A first prompt herdr saw no turn start for within 5 s records `prompt-unconfirmed`. The launcher then reads the pane: when the agent's input box still holds the prompt (Claude shows `[Pasted text #N …]` or the text itself) and the agent is not working, it sends one Enter, never the text again, records `prompt-resubmitted` and waits 5 s more. A runner that still has not started is reported as `stalled · prompt not submitted: …`, with the runner left open. An empty input, an agent already working, and a Codex, pi or omp runner, whose input is not read, change nothing.
- An agent blocked on a prompt in its pane is reported as `stalled`, with the last lines of the prompt: `stalled · blocked on a prompt: Do you want to proceed? / ❯ 1. Yes / 2. No`. The excerpt has secrets hidden and is at most 240 characters. A prompt the agent answers itself after a timeout, such as Claude Code's auto-denied safety prompt ("Claude Code will automatically deny this request in …", denied after 2 minutes), is only a `blocked` progress event; it becomes `stalled` news when it is still there 30 seconds after its timeout. A block that clears records `unstalled` with its duration, such as `unblocked after 2m01s`.
- An agent that stays `working` with no visible progress for `stallAfter` (10 minutes by default, see [config.md](config.md#keys)) climbs a ladder, each step once: a queued nudge (`nudged`), then `esc` and, if it is still working, one `ctrl+c`, followed by a prompt to continue (`interrupted`), then `stalled` news, `no progress for N min after a nudge and an interrupt; the runner is left open`. The kit samples the screen once a minute, without the agent's own animated status line and timers, and needs 3 samples before it acts. A retry the agent shows on its own status line is progress: after 3 times `stallAfter` of retrying, one `stalled` line says `retrying for N min`. A report, `send` or `answer` starts the ladder over, and so does visible work for a whole `stallAfter` after a step; a reply to a nudge alone does not. A prompt the agent answers itself that a `wait` saw is still escalated by the next `wait` when the first one ended. Nothing is failed or killed.

## Closing runners

A runner closes when `stop`, `gc`, `keep --off` past its close time or `cleanup --yes` ends it, and the event log gets a `closed` event that says whether the tab was kept. Before quitting the agent, the kit lists the processes the runner's pane started: its shell's process tree, and on Linux also every process that carries the runner's `HRK_TASK` and `HRK_STATE_DIR`, such as a server started with `&` whose shell exited, which leaves the tree. On Linux it also lists the processes in the runner's memory scopes, which still name them when herdr no longer has the runner's pane, as after a herdr restart. Those still running 3 seconds after the tab closed are reported once as `processes-left` news, such as:

```
t7 processes-left · fix login · 2 processes the runner started still run after its tab closed: 4123 `npm run dev`, 4188 `vite` (stop them yourself if not needed)
```

At most 3 are named, the rest counted, and secrets in their commands hidden. The kit never kills them. When the process list cannot be read, the close goes on and the event log gets `process-check-skipped`.
